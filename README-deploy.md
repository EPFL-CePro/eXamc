# eXamc — Deployment guide (staging / production)

This guide describes how to run **eXamc** in a server environment (staging or production).  
It is intentionally generic: adapt hostnames, paths, sizing and tooling to your own infrastructure.

> [!TIP]
> An **Ansible + Vault** setup that automates environment configuration and deployment is maintained in a separate repository: [**eXamc.ops**](https://github.com/EPFL-CePro/eXamc.ops).  
> Use it if it fits your infrastructure, or treat this guide as the reference for a manual or custom deployment.

## Stack

- Orchestration: **Docker Compose** (or your orchestrator of choice)
- Reverse proxy: **Nginx** (with **TLS**)
- App server: **Gunicorn** (WSGI)
- Services: **MySQL**, **Redis**, **Celery**, **Celery Beat**
- SSO: **Entra ID** (Azure AD) via OIDC

> [!WARNING]
> On staging/production: **no `runserver`**, **no auto-migrations on boot**, **HTTPS required**.

---

## 1) Prerequisites & secrets

- An environment file for the target (see *Environment files* in [`README.md`](./README.md) for the full list of variables). It can be written by hand from `.env.example` or generated by your configuration tooling (e.g. [eXamc.ops](https://github.com/EPFL-CePro/eXamc.ops)).
- Secrets provided through a secrets store or secured files, never committed:
  - `SECRET_KEY`
  - `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD`
  - `OIDC_CLIENT_SECRET`
  - TLS certificates (`.crt` / `.key`) if not using ACME
- DNS records for each environment, e.g.:
  - staging: `examc-staging.example.org`
  - production: `examc.example.org`

## 2) Caddy

Caddy is the only entry point: it terminates TLS on ports 80/443, redirects HTTP to HTTPS, serves the static files and proxies everything else to Django (Gunicorn). There is no Nginx and no reverse proxy on the host.

Configuration lives in `compose/deploy/caddy/`, mounted read-only at `/etc/caddy`:

```
compose/deploy/caddy/
├─ Caddyfile
└─ tls/
   ├─ internal.caddy   # dev + staging: certificate from Caddy's internal CA
   └─ certs.caddy      # prod: certificate from the tls_crt / tls_key secrets
```

**`Caddyfile`** (shared by every environment):

```caddyfile
{
	servers {
		timeouts {
			read_body 1h   # slow/big uploads
			write     1h   # slow downloads
			idle      5m
		}
	}
}

{$SITE_ADDRESS} {
	import tls/{$CADDY_TLS_MODE:internal}.caddy

	request_body {
		max_size 15GB
	}

	handle /healthz {
		respond "ok" 200
	}

	handle_path /static/* {
		root * /static
		header Cache-Control "public, max-age=604800"
		file_server
	}

	handle {
		reverse_proxy django:8000 {
			transport http {
				dial_timeout  1s
				read_timeout  1h
				write_timeout 1h
			}

			# Django in maintenance mode (503): show the static maintenance page
			@unavailable status 503
			handle_response @unavailable {
				root * /var/www/html
				rewrite * /maintenance.html
				header Retry-After 120
				templates
				file_server {
					status 503
				}
			}
		}
	}

	# Django unreachable (down, restarting, timeout)
	handle_errors 502 503 504 {
		root * /var/www/html
		rewrite * /maintenance.html
		header Retry-After 120
		templates
		file_server
	}
}
```

**`tls/internal.caddy`:**

```caddyfile
tls internal
```

**`tls/certs.caddy`:**

```caddyfile
tls /run/secrets/tls_crt /run/secrets/tls_key {
	protocols tls1.2 tls1.3
}
```

Caddy forwards the original `Host` and sets `X-Forwarded-For` / `X-Forwarded-Proto` itself; Django trusts them through `SECURE_PROXY_SSL_HEADER` and `USE_X_FORWARDED_HOST`. Request bodies are streamed to Django, not buffered to disk.

### Environment variables

| Variable | Purpose | Example |
|---|---|---|
| `SITE_ADDRESS` | Names/IPs Caddy serves, comma-separated (required) | `examc.epfl.ch` / `localhost:8443` |
| `CADDY_TLS_MODE` | `internal` or `certs` (default `internal`) | `certs` |
| `CADDY_PORT` | Dev only: port in `SITE_ADDRESS` and the port mapping | `8443` |

On servers, Ansible renders these from `site_hosts`, `caddy_tls_mode` and `caddy_port` (see `templates/.env.j2` in the Ansible repo).

### Certificates

- **dev / staging** (`CADDY_TLS_MODE=internal`): Caddy issues a certificate from its own CA. Browsers warn until you trust the root CA, found in the `caddy_data` volume at `caddy/pki/authorities/local/root.crt`.
- **prod** (`CADDY_TLS_MODE=certs`): the certificate (**full chain**: your certificate, then the intermediates) and the private key are Compose secrets `tls_crt` / `tls_key`, deployed by Ansible from the vault. The certificate must cover every name in `SITE_ADDRESS`, IP addresses included.

To renew: update `tls_crt` / `tls_key` in the vault and run the playbook (Caddy is recreated).

### Maintenance page

`compose/deploy/maintenance/maintenance.html` is shown when Django is unreachable (502/504) or in maintenance mode (503). It is a Caddy template: it shows the status code and the logo of the current environment (`eXamc-<ENV>.svg`, inlined, so no extra request is needed while Django is down). The folder is mounted at `/var/www/html` and edits apply without restarting Caddy.

Keep the page self-contained (inline CSS, no links to `/static/…`), and avoid `{{` outside template expressions.

### Compose mounts and ports

```yaml
  caddy:
    image: dhi.io/caddy:2.11.7
    volumes:
      - ./deploy/caddy:/etc/caddy:ro
      - ./deploy/maintenance:/var/www/html:ro
      - static_volume:/static:ro
      - caddy_data:/data        # certificates + internal CA (must persist)
      - caddy_config:/config
    secrets:                     # prod only
      - tls_crt
      - tls_key
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"            # HTTP/3
```

In dev, only `127.0.0.1:${CADDY_PORT}:${CADDY_PORT}` is published.

### Troubleshooting

The image is hardened (no shell). To look inside:

```bash
# Files as Caddy sees them (same mounts, same user)
docker run --rm -it --volumes-from examc-prod-caddy-1 --user 65532 busybox sh

# Config as loaded
docker exec examc-prod-caddy-1 caddy adapt --config /etc/caddy/Caddyfile --pretty
```

For verbose logs, add `debug` to the global options block and restart Caddy.

> **Private media:** files under `/private_media` are served by Django (signed URLs), not by Caddy, which doesn't mount that folder. If you later switch to `X-Accel-Redirect` (`PRIVATE_MEDIA_URL = "/_protected/"`), Caddy needs the folder mounted read-only and a `handle_response` block that serves the path from the header.

## 3) Gunicorn (django)

- Start Gunicorn from the **entrypoint** or the Compose `command`, e.g.:
  ```bash
  gunicorn examc.wsgi:application -c /app/gunicorn.conf.py
  ```
- Suggested tuning (adjust to CPU/RAM):
  - workers = `2*CPU + 1` (or start with `4–8`), class `sync` or `gthread`
  - timeout = `120` for heavier views (otherwise `30`)
  - `accesslog` / `errorlog` to stdout

> In production: `DEBUG=0`, `SECURE_SSL_REDIRECT=1`, cookies `*_SECURE=1`, **HSTS** enabled (e.g. 6 months).

## 4) Release cycle

The commands below use `<compose-file>` and `<env-file>` as placeholders (e.g. `compose/compose.prod.yml`, which is also used for staging, and your environment file).

1. **Prepare artifacts**  
   Git tag (`vX.Y.Z`), build images (django / celery / celery_beat), push to your registry if you use one.

2. **Controlled stop** (if needed)  
   Deploying hot is possible, but schedule a maintenance window if intrusive migrations are planned.

3. **Start / update services**
   ```bash
   docker compose -f <compose-file> --env-file <env-file> up -d --build
   ```

4. **Migrations** (manual or CI job)
   ```bash
   docker compose -f <compose-file> --env-file <env-file> exec django python manage.py migrate --noinput
   docker compose -f <compose-file> --env-file <env-file> exec django python manage.py collectstatic --noinput
   ```

5. **Reload Gunicorn / Nginx**
   - Gunicorn hot reload:
     ```bash
     docker compose ... exec django kill -HUP 1
     ```
     or restart `django` (short interruption):
     ```bash
     docker compose ... up -d --no-deps --build django
     ```
   - Nginx:
     ```bash
     docker compose ... exec nginx nginx -t
     docker compose ... exec nginx nginx -s reload
     ```

6. **Validation**
   - `curl -I https://<your-host>/healthz` → `200`
   - Key user journeys: OIDC login, main views, protected download.

> When using [eXamc.ops](https://github.com/EPFL-CePro/eXamc.ops), steps 1–3 (environment file rendering and `docker compose up`) are handled by the playbook; migrations remain a separate, explicit step.

## 5) Celery & Beat

- **Celery worker** (needs Redis & Django):
  ```bash
  celery -A examc worker -l INFO --concurrency=8
  ```
- **Celery Beat** (database scheduler):
  ```bash
  celery -A examc beat -l INFO --scheduler django_celery_beat.schedulers:DatabaseScheduler
  ```
- Healthchecks: PID/port, or `celery inspect ping` via a script.

---

## 6) MySQL backups & restore

- **Backup** (cron/CI): `mysqldump` + gzip, stored offsite.
- **Restore**:
  ```bash
  gunzip -c dump.sql.gz | mysql -u"$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE"
  ```
- Ensure **utf8mb4** for tables and connections.

## 7) Logs & monitoring

- Nginx, Gunicorn, Django, Celery/Beat → stdout (collect with your log stack: syslog, ELK, Loki, Sentry…)
- Healthcheck: poll `/healthz` from your load balancer or monitoring (e.g. every 30 s)

## 8) Security

- HTTPS required (TLS ≥ 1.2)
- HSTS, `Secure` cookies, `SECURE_SSL_REDIRECT=1`
- Strict `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` per environment
- Rotate secrets regularly (DB, OIDC, `SECRET_KEY`)
- Keep base images and Python dependencies up to date
- Limit upload size at the proxy (`client_max_body_size`)

## 10) OIDC notes (Entra ID)

- Redirect URIs must match exactly (HTTPS + final host)
- Keep clock skew minimal (NTP)
- Scopes: `openid profile email` (extend as needed)
- `ALLOWED_HOSTS` / `CSRF_TRUSTED_ORIGINS` configured for your domains

---

## 11) Quick rollback

- Redeploy the previous image tag (`vX.Y.(Z-1)`)
- Restore the database if a migration cannot be reversed
- Reload Gunicorn / Nginx
